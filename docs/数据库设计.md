# 数据库设计文档（v4）

> 生成日期：2026-11-06（原 v4 增量文档通用化改写）
> 前置文档：`docs/开发约定.md`、`database/nft.sql`（v1~v3 26 张表 + v4 增量 14 张 = 41 张）
> 设计原则：**与具体 C 端解耦**。后续会对接不止一个 C 端，本库表只定义后台（账本）自身的模型；
> 各 C 端通过开放 API 接入，其自有库表如何存储与后台无关。

---

## 1. 总体架构与库策略

```
C 端 A / C 端 B / ...（各自的后端与库，互不感知）
        │  开放 API（appKey + 签名鉴权）
        ▼
我们后台（BuildAdmin / ThinkPHP8）＝ 唯一账本
        │  本库 41 张业务表（nft.sql 一次性建齐）
        ▼
MySQL（业务表全部无前缀裸表名）
```

- **账本唯一**：藏品/盲盒库存、空投、抽签、活动记账全部在本库；C 端只展示与发起。
- **命名约定**：`int unsigned AUTO_INCREMENT` 主键、`createtime/updatetime`（bigint Unix 秒）、金额一律**分**、`utf8mb4_unicode_ci`、新增表统一带 `is_deleted` 软删（回收站语义）。
- **框架安装约定：表前缀留空**（BuildAdmin 系统表即为 `admin_rule` 等裸名；模型层 `$name`/`Db::name()` 已同步）。

## 4. 库存池对账口径

```
库存池(藏品) = collection.issue_quantity            -- 发行量
             − collection.buy_quantity              -- 已售
             − 空投净发放                             -- airdrop_item: status=1 − status=0（target_type=1）
             − 盲盒占用                              -- Σ blindbox_prize(quantity − sent)（未开出部分）
             − 已销毁 + 已回收                       -- stock_log type=1/2
             − 置换空投                              -- stock_log type=3 − type=4
```

盲盒剩余可投 = `total_supply − sold_count − airdropped`（独立账，不吃藏品池）。

## 5. 多 C 端对接原则

- 后台为每个接入的 C 端分配 **appKey/secret**（走开放 API 层，appKey 维度可下发品牌主题色/Logo/模块开关，数据来源 `setting`）。
- C 端用户与本库 `user` 的映射在开放 API 层完成，不侵入业务表。
- 具体接口契约（活动/抽签/空投/盲盒/藏品查询等端点清单）另行输出《开放 API 契约》，与库表解耦——换 C 端不改库表，只加 appKey。
